# Repository guidance

- Maintain the fork on `downstream/patch-build`; application changes belong in the ordered downstream patch queue and are built from a prepared tree. See [downstream/README.md](downstream/README.md).
- `Release` is the sole full-platform test, build, packaging and publication gate. Do not launch standalone CI/Linux workflows, run local full suites/builds as a pre-release gate, or run another full validation before tagging. Commit and push the fixes to `downstream/patch-build`, then use the release script; a failed Release job already blocks publication. Small targeted checks for a concrete bug or this maintenance tooling are allowed, but must not duplicate the full Release pipeline.
- Use `bash downstream/release.sh --plan` for read-only release inspection and `bash downstream/release.sh` to tag the latest already-committed `downstream/patch-build` and wait for publication. The script does not stamp versions, create commits, or modify the patch queue or documentation. Release builds derive their version from the tag via `GITHUB_REF_NAME`. The wrapper queries the latest upstream release automatically and blocks if its tag commit differs from the configured pin; migrate and commit the pin and patch queue before retrying.
- An unpublished candidate may be retried; published releases, tags and assets are immutable. Changes after publication require a new fork version and tag.
- Do not initiate a real release without explicit authorization. See the downstream release guidance for prerequisites and details.
