# Repository guidance

- Maintain the fork on `downstream/patch-build`; application changes belong in the ordered downstream patch queue and are built from a prepared tree. See [downstream/README.md](downstream/README.md).
- All product adjustments must be implemented for Windows and macOS together: features, bug fixes, provider behavior, persistence, refresh scheduling, settings, wording and floating-window interactions. Never treat a one-platform change as complete or silently leave the other platform on an older implementation. Compare both implementations before editing, migrate both sides in the same task, and verify each affected platform with the available focused checks. Native APIs and layouts may differ, but user-visible capabilities and behavioral contracts must stay aligned. Explicitly report unavailable native verification; it does not excuse missing implementation. Any intentional platform-only exception requires the user's explicit approval.
- Keep corrections in their owning feature patches; the newest queue entry is not a catch-all. In the quota queue, macOS base Codex behavior, lifecycle, settings and floating-surface fixes belong in 0020; Windows base fixes belong in 0021; 0022 carries only the multi-window/OpenCode Go increment and its necessary integration. Move genuinely shared prerequisites to the owning earlier patch instead of leaving the base platform stale or hiding unrelated corrections in a later feature. Repartition dependencies when needed and prove the complete queue still applies with an unchanged final source tree.
- Do not routinely publish/package local development builds or place ZIPs/binaries in the repository root. That workflow was a temporary workaround for earlier floating-window display failures, not the default delivery process. Use focused checks and report their limits; create a local test package only when the user explicitly requests one or agrees it is needed for a concrete critical issue. Do not automatically trigger or repeatedly rerun GitHub Actions to chase UI verification; diagnose the actual failure and obtain authorization for a new release run. Missing native/live-account verification must remain explicitly unverified, not cause an open-ended packaging/Actions loop.
- Do not use automated tests to validate drawing or visual appearance on either platform. Quota pixel/color/snapshot, glyph/path, contour/topology, raster/filter-output, layout-coordinate and shape-point assertions must not become ordinary test or Release gates, including tests disguised as hit-region geometry checks. Keep genuine nonvisual provider, persistence, lifecycle, hover/drag ownership and animation-state tests. Verify appearance on the actual native surface or with explicitly manual visual diagnostics; if that environment is unavailable, report the drawing as unverified rather than replacing visual acceptance with assertion counts, extracted geometry scripts or another CI run. Do not add replacement drawing tests when removing these gates.
- Subscription quota providers must use [Codenotch at the pinned reference commit](https://github.com/vinzdg/codenotch/tree/835550a342871779135b6484d6899161c5222f7c) as the first implementation reference, not just a visual reference. Inspect its existing provider, credentials, usage parser, endpoint selection, status handling and backoff before researching or designing a new integration; use official supplier sources to verify differences, not to restart discovery from scratch. In particular, OpenCode Go already has `OpenCodeProvider.swift`, `OpenCodeCredentials.swift`, `OpenCodeUsage.swift` and `OpenCodeSchema.swift` in `Sources/Providers`. Port the applicable behavior into our native architecture and preserve license attribution when copying code; do not import unrelated providers or change the reference pin without an explicit upgrade decision. See downstream quota guidance for known credential-route differences.
- `Release` is the sole full-platform test, build, packaging and publication gate. Before release mutations, the wrapper prepares one tree and runs local preflight: on Linux and macOS, a Windows Release solution build and the `net10.0` Core and Presentation tests; additionally, Linux runs a headless CMake build and CTest, while macOS runs `swift test`. Linux excludes four Windows Core tests requiring unsupported `FileIdentity`; macOS does not filter them, and native Windows `Release` runs all four. See the downstream README for their names. This requires the .NET 10 SDK plus the host's CMake/C++ dependencies or Swift toolchain. Host-specific checks do not validate the other OS, native UI or release packaging; these remain with `Release`. `--plan` skips preflight and its toolchain requirements. Do not launch standalone CI/Linux workflows or duplicate the full Release pipeline locally. Small targeted checks for a concrete bug or this maintenance tooling are allowed. Commit and push the fixes to `downstream/patch-build`, then use the release script; a failed Release job blocks publication.
- Use `bash downstream/release.sh --plan` for read-only release inspection and `bash downstream/release.sh` to tag the latest already-committed `downstream/patch-build` and wait for publication. The script does not stamp versions, create commits, or modify the patch queue or documentation. Release builds derive their version from the tag via `GITHUB_REF_NAME`. The wrapper verifies that the configured upstream tag resolves to the pinned commit and blocks on a mismatch. A different latest upstream release produces a warning; releases remain on the pin. Only when choosing to upgrade, manually migrate and commit the pin and patch queue.
- An unpublished candidate may be retried; published releases, tags and assets are immutable. Changes after publication require a new fork version and tag.
- Do not initiate a real release without explicit authorization. See the downstream release guidance for prerequisites and details.
