## v1.6.1-fork.1

This downstream release is based on upstream Agent Speed v1.6.1 and adds opt-in remote Linux agent monitoring to the macOS app. It also includes the macOS Remote hosts settings compilation fix. See the [upstream v1.6.1 notes](v1.6.1.md) for the baseline changes.

### Remote monitoring

- Configure an SSH host alias for the Linux account that owns the agent logs in `~/.ssh/config`, pre-trust its host key, and use noninteractive key or SSH-agent authentication. Enable the host in **Settings → Sources**. Remote monitoring is independent of the app's network switch; disable the host to stop it.
- The app uploads its bundled collector and runs it over SSH standard streams. It does not require a listening port, HTTP service, Python or sudo. The collector reuses the Linux measurement core, including omp parsing and parent/child deduplication.
- Local and enabled remote hosts are simultaneous standard sources, grouped by host and source in the existing native dashboard. Available statistics contribute to the native aggregate; there is no dashboard target switch. Offline hosts are identified as offline, and unavailable data and offline history gaps are not treated as zero. History export matches the visible history. Local diagnostic reports exclude remote data.
- The collector maintains a private history cache at `~/.cache/agentspeed-collector/history.sqlite3` on the Linux host. Concurrent collectors or an unsafe or unavailable cache use memory instead. Changes to monitored source configuration reset the cache.

### Limitations and verification status

- **Real SSH end-to-end operation on an actual remote host has not been verified.** Build and automated checks do not establish host compatibility or validate the complete connection, disconnect and reconnect experience.
- The bundled collector supports **Linux x86_64 only**. Linux desktop packages for other architectures do not imply collector support. The collector is dynamically linked; the remote host must provide compatible runtime libraries. An unsupported architecture or incompatible system cannot use the bundled collector as-is.
- Metrics depend on what the logs record. Missing fields remain unknown; live rates inferred from recent completed responses are estimates. omp commonly records responses only when complete, so per-token streaming speed and unrecorded time to first token cannot be measured; router retries and account cooldowns absent from logs are also unknown.
- The remote protocol can provide source, agent and history aggregates, but does not provide categorized today's tokens, project paths, traffic or continuous curves. Unavailable data stays unknown rather than being presented as zero.
- Initial history scans can take considerable time and resources on large log collections. A `partial` history flag reports known discovered-file and database errors, but a clear flag does not guarantee exhaustive discovery or filesystem readability.
